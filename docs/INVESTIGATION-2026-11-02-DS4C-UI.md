# 2026-11-02 frontend failure while loading a mod

## Evidence captured before changes

The supplied `log1.txt` and `log2.txt` are byte-identical dev.53 captures. They
do not cover the reported DS4C reproduction. The supplied persistent crash log
mostly repeats older dev.52/dev.53 data. To get a relevant capture, the
console's current `/data/BO3-Customs/log.txt` and `/data/BO3-Customs/crash-errors.log`
were read over FTP; only file listings, timestamps and sizes were read for
console SPRX files. The console currently has dev.59 installed (FTP size
557,024 bytes); the retrieved session itself was generated by dev.58.

The dev.58 session explicitly selects `^6ds4c`, loads its core and ZM zones,
then reaches the first UI failure after frontend initialization:

```text
UI Error 40092 ... DS4C_ProgressionStore.lua): 3778239045:629: attempt to index a nil value
  3778239045:629 in function '(*stripped)'
  [C] in function 'require'
  269117547:11 in function '(*stripped)'
  [C] in function 'require'
```

The stack does not identify the nil operand or name the stripped function.
Afterward, BO3 reports `LUI Error: Tried to add nonexistent menu main` and then
`... menu Lobby`. The frontend error handler pauses additional compatibility
injection for that failed frontend generation; this is existing recovery logic,
not the originating nil dereference. The later missing-menu errors are
consistent with an incomplete menu build and should not be treated as an
independent engine crash without more evidence.

No native crash, kernel panic, or map-load failure is recorded in this session.
The map count is 39. `crash-errors.log` ends with the same dev.58 UI error and
menu errors. Its `.1` file includes older dev.53 diagnostics and unrelated
third-party GSC runtime errors; those are not evidence for this reproduction.

The failing function hash also appeared in the earlier Reaper incident, where
offline bytecode inspection tied a different instruction in that function to a
missing PC watermark class. Here the failing instruction is 629 (not 252),
and the immediately preceding loaded rawfile is a different mod UI module.
Matching hashes alone do not prove the nil operand is the watermark. The prior
missing-class fallback is generic and remains in current source, but must not
be described as a fix for this DS4C failure without resolving this instruction
or testing the same frontend on dev.59.

## Root-cause status and safe options

The evidence proves an unhandled Lua nil-index in a mod UI callback during a
frontend rebuild, followed by attempts to add menus that do not exist. It does
not prove which global/table is nil or that BO3-Customs native code caused the
first exception. The first exception is inside stripped code associated by the
engine with a third-party rawfile. The mod's distributable contains compiled
fastfiles rather than editable Lua sources.

Before changing runtime behavior, resolve the function's bytecode/instruction
against the exact loaded fastfile where possible and review the generic UI
error/rebuild boundary. Do not blanket-fill nil values, swallow every script
error, clear package/module state, or unload a selected mod on a single UI
exception: each can conceal incompatibility or corrupt otherwise working mods.
Preflight can validate files and bytecode readability, but cannot prove
runtime-dependent Lua globals are non-nil.

The DS4C rawfile was present in the locally available mod fastfile, but its
payload does not have the expected Havok Lua chunk header; this copy cannot be
parsed with the project's existing bytecode reader. The error's instruction
therefore remains unresolved. A separate recovery gap is confirmed in our own
source: after an exception, the injection latch is reset only when a frontend
zone is about to load. The existing AddMenu hook already observes a later
successful `main` registration, but does not clear that latch. A narrow repair
can re-arm compatibility injection only after that positive signal, resetting
state-local caches before retrying. This cannot fix the original nil access or
the failed `main`/`Lobby` registrations in this capture; it makes a later,
successful menu rebuild recover instead of remaining latched.

## Source correction

`AddMenu_h` now clears the failed-generation latch only after the native
`AddMenu("main")` call returns successfully. It clears cached UI utility/mouse
state, marks the current main state ready, and schedules the existing normal
injection path. Other menu names do not re-arm recovery. If the native main
registration throws, the hook does not reach the reset. A focused ASan/UBSan
host regression exercises main-menu recovery and verifies a non-main menu
leaves the latch set. This improves recovery after the UI becomes valid again;
it is not a repair to the original third-party Lua callback.

## Validation boundary

Host fixtures and static analysis can validate safe guards, diagnostics and
state ownership. Only a console run can show whether dev.59 or a later build
preserves the DS4C menus and other mods. Missing assets and the absence of a
native crash in these logs do not establish broad map stability or kernel-panic
prevention.
